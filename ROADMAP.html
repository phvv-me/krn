krn.py

krn is a typed Python kernel language for writing fast CPU and GPU code that remains easy to read and extend. Prove low-level performance and Pythonic contracts through small reusable libraries before expanding languages or hardware; Python comes first, owned runners through M4, and each milestone ends with five guides and cumulative evidence.

Expand each feature for its tasks, acceptance cases and references. Milestone order is not a global execution barrier.

    • [ ]1.1krn.configure · Numerical requirements

      Owner discussion before changes to arithmetic or defaults.

      • [ ]1.1.1Define the promisesDecision

        Keep arithmetic semantics, accuracy, reproducibility and implementation strategy separate.

        # Same float64 operands; only the addition order changes.
a, b, c = 1e16, -1e16, 1.0
left = (a + b) + c   # 1.0
right = a + (b + c)  # 0.0
        • [x]1.1.1.1Native defaultDecision

          Owner decision. Explicit repeatable and portable requests must be satisfied or refused; neither promises every device or shape.

        • [ ]1.1.1.2Native policy

          Proposed default for bulk operations: select a target implementation within declared dtype, rounding and accuracy constraints. Native does not mean arbitrary fast math or silent precision loss.

        • [ ]1.1.1.3Repeatable policy

          Require identical output bits for identical inputs and a declared execution envelope: algorithm, target, compiler/driver/library versions, workspace, streams and launch settings.

        • [ ]1.1.1.4Portable policy

          Require identical bits across a named target/operation/dtype set. An unmet request raises an explained error; “best effort” is a diagnostic result, not a guarantee.

        • [ ]1.1.1.5Name allowed changes

          Treat batching, layout, tiling, partitioning and software upgrades as separate invariance claims. Preserve the same logical inputs/output; changing the reduction length generally changes the problem.

          • [ ]1.1.1.5.1Batch case

            Compare one row alone and embedded in a larger batch; preserve its operands, reduction dimension and output mapping.

          • [ ]1.1.1.5.2Padding case

            Mask extra lanes by validity. Specify NaNs and signed zero; do not assume adding numeric zero preserves every bit.

          • [ ]1.1.1.5.3Layout case

            Compare equivalent contiguous and strided views, then tile/block choices. Distinguish a changed address mapping from changed values.

      • [ ]1.1.2Keep scalar meaning explicit

        Preserve written evaluation order and explicit FMA. Settle integer overflow, signed floor division/remainder, oversized shifts, NaNs, signed zero and subnormals.

        • [ ]1.1.2.1Empty mean

          Raise ZeroDivisionError before launch for host-known zero reduction extents; transport a checked dynamic empty-row failure to the next synchronization boundary and attribute its logical row instead of claiming NaN implements the agreed contract.

        • [ ]1.1.2.2Division and shifts

          Current integer division by zero and oversized shifts return zero. Resolve this conflict with the Pythonic goal before documenting them as stable.

        • [ ]1.1.2.3FMA boundary

          One rounding is not exact real arithmetic. Matching bits also requires equal formats, rounding and special-value behavior. Do not claim unconditional cross-target FMA equality.

        • [ ]1.1.2.4Accuracy data

          Record exact/ULP/relative/absolute or algorithm-specific bounds with input domains. Distinguish a guarantee, vendor-tested limit and our measured sample.

            The seven current entries are Apple exp10/log10/pow/tan/tanh and NVIDIA pow/tan. State composition, domain and special values; no finite universal bound is required where it is unjustified.

            Use high-precision or interval references with correct input conversion, exponent range and subnormal treatment. MPFR precision alone does not reproduce an IEEE format.

            The current expected failures search documentation for a finite-bound pattern. Replace that premise with structured contract validation and separate numerical cases; never promote a sampled maximum to a universal guarantee.

          Perturb one factor at a time.

          • [ ]1.1.4.6.1Elementwise add

            Portable where rounding, subnormals and special values agree. Fused expressions need a contraction rule.

          • [ ]1.1.4.6.2Reduction

            Repeatability may pin a tree. Tile/partition invariance needs a canonical logical tree or reproducible accumulator. Padding is not always neutral for NaNs or signed zero.

          • [ ]1.1.4.6.3Tensor-core GEMM

            Native and fixed-envelope repeatability are useful. Portable bits may require a slower composed algorithm; opaque hardware steps are not a cross-generation guarantee.

          • [ ]1.1.4.6.4Atomic scatter

            A seed does not fix floating addition order. Use ordered segmentation or reproducible accumulation. Racing non-atomic writes remain invalid.

          • [ ]1.1.4.6.5Math and solvers

            Matching vendor accuracy does not imply equal bits. Portable transcendental functions need a shared algorithm. Repeated eigenvalues require residual/subspace comparisons, not equal eigenvectors.
